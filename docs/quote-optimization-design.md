# 顾客实付最优报价与门店讲解脚本设计

> v1.4当前执行基线：用户已授权继续本机Dify安装及业务搭建、修订提示词和准备参赛提交材料；先前“仅交文档”的范围已被后续指令扩展。知识来源采用用户确认的本地v7开发＋参赛ima实时/关联核验双模式，详见[知识源模式](knowledge-source-modes.md)。节点System与变量绑定以[提示词绑定指南](dify-prompt-binding-guide.md)、[提示词登记](../specs/prompt-registry.json)为准。不能用本地读取冒充API达标；实现、离线测试、平台导入、真实运行和参赛验收分别记录。

版本：1.4。用途：交给开发 Agent 在 Coze/Dify 工作流及确定性 HTTP 小服务中搭建。更新日期：2026-10-18（Asia/Shanghai）。本文规定报价领域设计；工具路径、状态、字段和云外发边界统一以[业务工具唯一逻辑合同](../specs/business-tool-contract.md)为准。当前没有已部署/联调服务、真实报价、运行成绩或可直接使用的销售脚本；开发时须落实严格Schema、OpenAPI与合同测试。

## 1. 已确认目标与来源现状

用户已确认：

- 四级名称已由用户确认：**基准价、平台优惠、身份权益、换新国补**；名称来源为 `user_confirmed`。各级实际金额、适用条件、组合关系和核算顺序仍须从 ima 取证，规则来源为 `ima_evidence_required`。
- **先确认销售平台、用户需求/资格与使用场景，再筛选有据适配的推荐产品；对每个推荐 SKU 求其规则内最低实付，最后在适配候选中比较实付。** 不拿不适配但便宜的产品替代推荐。
- 用户进一步确认：**本次现金支付最低，使用同一顾客已核验的权益和旧机条件**。保留`objective=min_customer_payable`兼容标识，精确指标为`objective_metric=min_cash_due_now_given_verified_customer_resources`、版本`1.0`。商品结算应付、已核验抵付和本次现金分别展示，旧机价值、积分消耗与余量单列；现金最低不等于旧资产/积分没有成本。
- 3 分钟脚本供**新店员向顾客讲产品并解释报价**；不是面向评委演示应用，也不是默认的员工操作培训。
- 正确率要求大于 95%；按第 9 节建立独立金标与可复核验收，不能先声称已达标。

主任务已在用户 ima 桌面核对 P4 目录及《对外报价合规检查.md》《渠道报价登记.md》《建议零售价快照.md》：这三份均为 **v0.1 受控空模板**，没有实际价格或内部阈值；要求只引用已核验且未失效的内容，不对外泄露底价、返利、审批等内部信息。目录有建议零售价快照、商城当日价快照及渠道、教育、补贴、套装、分期等登记入口。这些是来源定位线索，**不能据此推导当前实价、可用资格、叠加关系、核算基数或计算顺序**。四级名称已知，不代表相关规则已被知识库证实。

因此初始配置必须为：

```text
FourLevelsSpec.name_source = user_confirmed
FourLevelsSpec.rules_source = ima_evidence_required
FourLevelsSpec.source_status = pending-source-verification
FourLevelsSpec.semantic_kind = null
FourLevelsSpec.levels = four_named_level_records_with_unverified_rule_refs
FourLevelsSpec.calculation_order_ref = null
FourLevelsSpec.stack_policy_ref = null
PricingRuleSet.publication_status = unverified
real_quote_enabled = false
```

levels的严格四条对象结构见 [配置样例](../specs/quote-configuration.example.json)，每条带level_id/display_name及空rule_refs，不将名称直接当可执行规则。

`pending-source-verification` 现在专指实际价格、适用条件、运算语义和组合规则待 ima 核验，**不是四级名称未知**。四级列表的展示顺序不等于计算顺序，四项也不默认全可叠加。空模板不能当价格规则或金标；模板中的“须核验”也不是相关资料已经核验的证据。可先实现接口、引擎、合成夹具和阻断流程；真实报价开关只在完整规则取证、审批发布和验收后开启。

按用户指示完成的商城官方公开查询见核验记录（本地记录或生成材料，未随公开源码发布），候选映射见[官网规则候选](../specs/commerce-rule-candidate.example.json)。官网一般规则仅为`pending_kb_ingestion`候选，未写入指定ima、未构成当前SKU/顾客的可执行规则，当前仍`real_quote_enabled=false`。商城帮助把回收代金券视为支付工具而非额外销售折扣，说明必须分账；它没有证明实际余额、回收最终值或教育/国补跨级叠加。**现金优化目标由用户确认，实际计算规则仍待知识源核验和授权发布**，不能用目标确认替代规则核验。

本文新增报价计算和客户讲解脚本能力，仍不包含交易、下单、业务预算预占、底价审批或自动向公共平台发布。

正式`marketing/full_package`输出默认`quote_required=true, purchase_plan_required=true`：必须交付四级组合比对后的获准最优购买方案，并按已确认内容平台、人群和场景生成对应话术，不能只输出一个“最终价”。显式`product_intro`或开发阶段无价链路可独立运行，但不计正式完整成品。报价来源/权限/完整比较不足时继续可独立验证的开发内容，正式完整包标受阻，不用无价稿冒充完成。

## 2. Coze/Dify 的默认搭建方式

采用“平台工作流 + HTTP Tool 确定性报价服务”。报价小服务可与已有知识库、渲染和鉴权服务合并部署；不为此单独搭建完整前端或额外多智能体系统。平台 LLM 负责理解用户、补齐输入和解释**获准外发**的结果；金额计算、规则适用性、候选空间、最优性和最终导出门禁由服务端代码负责。

```text
平台：输入/身份 → 确认销售平台、用户与场景 → 有据产品适配筛选
服务：鉴权 → P4四级实际规则核验 → 规则快照
      → 冻结同一顾客已核验资源与允许使用范围
      → 每个适配SKU的完整销售/资源组合候选域 → SKU内精确求解/独立回放
      → 同口径SKU间现金比较及覆盖检查 → 授权客户报价/比较摘要
平台：只接收获准最小字段 → 推荐事实+对应SKU报价快照 → 客户讲解脚本
服务：金额及限定条件比对 → 保密检查 → 版本与有效期门禁 → 导出
```

### 2.1 机密资料与云平台边界

P4 标记机密，默认**不上传 Coze/Dify 云端知识库、不送云端 LLM、不放入公开 Demo、仓库、截图、日志、视频或公开链接**。开发 Agent 可以在用户授权的 ima 环境只读定位资料；这不自动授权把原文、内部规则或派生价格发给第三方模型。

区分两层授权：

1. `source_access_policy`：本地/受控服务能读取哪些 P4 资料，属于哪个租户/门店，是否允许编译成规则，是否允许发给指定模型/地域。
2. `client_quote_disclosure_policy`：哪些**计算后客户字段**可给顾客、平台工作流、特定模型或某个内容渠道；这些去向逐项判定，不因顾客可见就默认能发云端或公众号。

`CustomerQuoteSummary`是唯一客户摘要Schema；`ClientQuote`仅为其同义名，不维护第二套字段。最小白名单摘要仍需按purpose、目标平台/provider及region逐项授权才能进入云工作流。默认云端仅收到安全状态、不透明报价引用及可公开补充信息；内部rules、applied/rejected明细、候选/替代方案、proof及内部账本不外发。未获准时私密结果保留受控服务，必要时由本地确定性模板合成客户可见稿，私密成稿不再回流云平台。授权未完成不能承诺云端自动生成含真实报价的脚本。

服务端保存 ima 凭证、原文访问 Headers、规则全文及内部账本。报价工具只持有限权限服务凭证，不持ima或其他服务主密钥；平台原生模型供应商凭证另按获准workspace/租户策略管理。租户、操作者和门店范围从认证会话/受限集成身份解析，不能信任 LLM 传来的 `tenant_id`、角色或任意来源地址。共享平台凭证必须限制到租户与获准用途，并有可核验的最终用户身份映射；仅靠输入一个门店名不构成授权。

## 3. P4 规则核验与 FourLevelsSpec

### 3.1 已确认名称，按 ima 核验实际运算关系

| level_id | 用户确认名称 | 仍须 ima 证实的内容 |
| --- | --- | --- |
| `base_price` | 基准价 | 本次 SKU/配置、平台/门店与时点应采用哪一个有效价格来源及金额；不能自动把建议零售价或商城快照认作基准。 |
| `platform_discount` | 平台优惠 | 本次实际销售平台可用规则、资格、候选、基数、门槛、限额、有效期、与其他级关系。不能把内容发布平台当成交平台。 |
| `identity_benefit` | 身份权益 | 来源明确的身份资格、核验方式、适用范围及权益如何进入金额；不明身份不默认符合。 |
| `trade_in_national_subsidy` | 换新国补 | 这一名称下实际包含的政策/规则、资格、商品/地区/时间范围、金额或比例、上限、申请条件和与其他级的关系，全部按 ima 有效资料。不能凭常识推定国补比例、旧机条件或可叠加性，也不擅自拆成额外级。 |

`name_source=user_confirmed` 与 `rules_source=ima_evidence_required` 分开记录；用户确认四级名字不是确认任何真实政策。开发 Agent 不再追问四级名字，而应只读核验资料并在必要时报告具体缺规则项。

编译前仍检查来源究竟描述互斥价格档（`pricing_tiers`）、有序计算阶段（`discount_stages`）、多组选项（`option_groups`）或基准加条件组件的混合结构。此分类只决定准确引擎表达，不改变四个已确认名称，也不强迫四项都按同一运算类型执行。`semantic_kind` 在规则核验前保持 null；若实际为混合结构，应以版本化受限表达承载并做合同测试，不硬套“四个价格相加”或“四次扣减”。

`FourLevelsSpec` 记录各级候选来源、基数、空选项/不适用语义、互斥/叠加、依赖、真实核算顺序、舍入与上限、适用范围、资料定位/哈希、有效期、核验人和发布版本。不适用需有规则依据；未知不能当零优惠或可任意跳过。缺必要运算规则/关系、有效来源冲突时阻断真实求解，名称仍保持已确认。

### 3.2 从资料到可执行规则

按指定库和 P4 实际目录只读检索；搜索空时浏览目录并分页。型号必须唯一到 SKU/配置；销售渠道和内容发布平台分字段。资料分为：已核验且有效、待审核、历史/过期、冲突、空模板。只有已核验且有效且有相应使用授权的资料能进入发布规则。

每条规则保留：

- `rule_id`、tenant/store/SKU 配置/数量/渠道/地区/币种/资格条件。
- `effective_from/to`、时区、边界语义、源资料版本、来源定位/哈希。
- 白名单计算表达与输入基数；叠加 `stack`、互斥 `exclusive`、依赖 `requires`、顺序 `order`、各级/累计 cap、floor。
- 舍入时点、模式、单位；分摊和尾差归属；必要费用、税费及其计算口径。
- 如真实规则要求，再登记业务预算/配额、成本/利润底线及审批条件；这些只在服务端参与约束，不对外显示。
- 草案、已核验、已发布、撤销状态及授权审批记录。

规则由受控 DSL/Schema 编译，禁止 `eval`、外部 Markdown 任意命令或 LLM 返回的可执行代码。可用 LLM 提取规则草案，但 P4 默认不外发；真实规则发布需业务授权角色核验，不能模型投票后自动生效。来源缺失、有效期不明、资格未知、叠加或舍入不明不能默认通过。

## 4. 输入、金额与完整候选域

### 4.1 先适配推荐，再为每个 SKU 建立 QuoteContext

先确认 `sales_platform`、用户需求/必要资格、使用场景、预算等已表达约束和本次门店范围；缺少影响推荐或报价的必要条件先补齐。`content_channel` 只表示文案发布渠道，不能替代实际销售平台。对知识库有资料支持的产品建立 `RecommendationSet`：每个候选含准确型号/配置、适配理由与事实引用、必要限制、适配/不适配/待确认状态，以及排除理由。不得编造适配能力、给无依据推荐分或为了低价放入不适配产品。适配不明先补证，不静默判为适配。

仅对已证实满足必需需求的适配候选计算；每个推荐 SKU 的 QuoteContext 必需字段：获准 tenant/store/actor、`recommendation_set_ref/version`、唯一 SKU/配置、数量、实际销售渠道/平台、地区、报价时点及规则时区、币种和最小单位、顾客资格及必要证据、`customer_resource_snapshot_ref/version`、`resource_use_scope_ref`、四级规则版本、该 SKU 完整销售/资源组合候选范围、`objective / objective_metric / objective_metric_version`、报价有效期。

资格采用 `verified / not_eligible / unknown`，只收所需最少资料。未知资格若可能改变最优，必须补齐，不能默删潜在更优选项。不同产品的 quantity/套装内容、需求满足程度和计价口径须明确；不能把不同数量、币种或不等价购买范围直接按裸数字混比。最终选定某 SKU 后，脚本与报价只能绑定这个准确型号/配置，不将另一产品的低价挂到当前演示机。

资源快照需核验同一顾客已拥有/满足的权益、积分和券余额/有效期/适用限制、旧机条件、质检最终回收值及发券可用状态；本次允许使用的资源集合/上限经顾客确认后由`resource_use_scope_ref`冻结。初估、待到账、未来本单奖励与未知余额均不视为可用资金；不得为求更低现金换任意旧机、伪造身份或无限积分。资源不参与且已核验时可用空集合，未核验不等于空集合。权益/余额若影响最优而未知，阻断有效报价并补齐。该确认仅用于报价，不授权实际回收、兑换、支付或下单。

跨SKU比较是同一顾客对不同购买方案的反事实比较：每个方案都用同一个冻结资源池，不依计算先后消耗余额，也不能给较贵SKU凭空增加资源。若实际同时购买多台，必须按整个购买范围联合约束资源总量与限购条件，不能把分别最优的同一券或旧机在合计账单使用两次。资源/允许使用范围变化需重新求解并使旧报价、比较和脚本失效。

### 4.2 Money 与 ArithmeticPolicy

币种以分计价时使用整数分；其他币种按其已核实最小单位配置。比例和中间计算使用 Decimal 字符串/整数或精确分数。禁止二进制 float 输入金额，拒绝 NaN、Infinity、超界、非法精度；JSON、数据库和求解器边界分别验证。前端超出安全整数范围时传整数字符串。

每条计算路径固定精度、舍入阶段/模式/单位与尾差策略，用任务局部上下文计算。不能默认银行家舍入、逐级舍入或最终一次舍入；按来源规则执行，缺失就阻断。送入 CP-SAT 前校验系数缩放及 64 位表达范围，不能通过有损截断或溢出获得“精确”金额。[Python Decimal 官方文档](https://docs.python.org/3/library/decimal.html)

采用分层账本，金额定义及DTO以唯一逻辑合同为准：

```text
merchandise_total_minor：已核验销售折扣/补贴后的商品结算应付，未扣支付工具。
mandatory_fees_minor：未计入商品结算的全部必计运费、税费和服务费。
order_total_before_payment_minor = merchandise_total_minor + mandatory_fees_minor
credits_applied_minor：已核验且本单可用的非现金支付抵付，按限制只扣一次。
cash_due_now_minor = order_total_before_payment_minor - credits_applied_minor
customer_payable_minor = cash_due_now_minor（兼容投影，禁止独立改值）
```

所有项须按规则算至最小货币单位、非负，抵付不得超过相应允许抵付的应付额。运费或其他费用可能受优惠/积分使用量影响，须在每条候选路径按真实规则回算；未知费用即使不影响排序也不能给完整有效报价，不默认包邮或0元。已含于商品结算的税费不重复加。

积分按已核验规则归入销售减项或支付抵付，不能两处减；无论分类，实际消耗点数与余额均单列。回收代金券是支付工具，同一旧机回收价值不再从商品应付或现金中扣第二遍；实际额外换新补贴与国补按各自条款另记，不把所有项目都按第四级重复扣减。旧机初估不当已质检最终值，未到账或不能用于本单的券、未来购物奖励、礼品及未核实返还不抵本单现金。不得默认把分期首付/订金当全额结清现金来优化；若顾客另选融资/分期，先明确新的购置范围、全部债务及费用，不能沿用本口径隐瞒未来负担。

只用于算术合同测试的**合成示例，非华为真实商品/规则/报价**：商品结算应付100000分，已核验必计费用1000分，本单允许的回收代金券抵付15000分、其他已核验支付抵付5000分，则订单支付前应付101000分、抵付20000分、本次现金81000分。假设该券由旧机最终回收价值15000分产生，该价值只作资源说明，不再次相减；这些数额和可用关系均不能用于真实营销或报价。

### 4.3 候选完整性

为每个适配 SKU 建立独立 `CandidateManifest`，记录本次范围、来源/目录分页、四级可用选项及必要规则版本、同一资源快照与允许范围、全部合法抵付组合/用量及费用联动、完整性与未决项。完整性覆盖销售优惠与资源使用两层；仅取最大积分或全部券组合未必满足运费、上限、互斥、最低现金规则。Top-k 检索、首屏目录或模型列出的几种方案不构成完整价格候选域。

再建立 `ComparisonManifest`：推荐集及其版本/适配依据、适配 SKU 总数、已完成有效报价 SKU 数、未完成及原因、每 SKU quote_ref/quote_version/validation_ref、币种/数量/购置范围、目标版本、资源快照/允许使用范围一致性与比较覆盖范围。内部完整清单留受控服务，对客仅按授权输出最小比较摘要。商品结算最低与现金最低可能不同，不能偷换列或把资源消耗不同的方案称为同等总成本。

只有 SKU 内候选及影响排序规则完整，才证明该 SKU 价格最优；只有本次适配集全部应比较 SKU 都完成同口径有效报价，才能宣称本次适配集内最低实付。若部分 SKU 缺规则/费用/资格或报价未证最优，允许展示获准已完成子集并明确覆盖缺口，但不得称整个推荐集最低。四级全叠加、默认各选一、未知视为零或任意跳级均禁止；空选/不适用必须有来源。

## 5. 精确优化与结果证据

目标固定为：

```text
第一层：以平台、用户和场景的有据必需需求筛选适配推荐SKU集合S。
第二层：冻结同一顾客已核验资源R、已确认允许使用范围U及目标metric/version；
        对每个i∈S，在其完整合法四级销售候选与资源使用候选域Fi(R,U)内：
        Pi = min cash_due_now_minor(i, sales_combination, resource_use)
           = min customer_payable_minor(i, sales_combination, resource_use)
        subject to 全部适用已核验销售规则、费用、资格、资源余额/限制及硬约束。
第三层：仅在同一R/U/目标版本、可比、适配且有效报价覆盖完整的S内，比较min(Pi)。
        覆盖不完整时只能比较并披露已完成子集，不声称S全域最低。
```

推荐适配门槛先于价格优化，不以不适配的便宜产品替代推荐，也不以低价抹去不同产品的已知能力差异。不在目标中暗加利润最大、库存优先或某渠道偏好；真实利润/预算限制若存在，作为销售硬约束。

保留每 SKU 内等价最低现金组合及跨适配 SKU 的等价现金候选，显示获准的产品/条件、商品结算、抵付、旧机价值/积分消耗及余量差异。现金相同不表示经济总成本相同；未批准资源偏好/并列策略时不伪称唯一最优，不暗选会多耗积分、兑换券或交付旧机的方案，也不以内部利润暗选一解。稳定ID只决定展示顺序；客户选方案与实际不可逆操作另行确认，本应用报价不执行操作。可证明最优金额而保留多个最优资源方案，不把尚未选定的资源路径包装成已执行结果。解释结果还须交代：为何产品适配、四级有据适用关系、核算与舍入、支付工具不重复扣减、SKU内最优证明和跨产品覆盖范围。内部底价/返利/审批及完整证明不进入客户摘要或云模型。

### 5.1 默认完整枚举

首版优先精确枚举已核实的有限空间。若实际语义是每组选一，才枚举 `D1 × D2 × D3 × D4`；多选、价格档或有序阶段分别按其语义构造，再纳入同一资源池内全部合法使用组合/用量。每个候选执行适用性、组合约束、逐步金额/舍入、费用联动、资源余额/限制与硬规则检查，分别计算商品结算、抵付和本次现金，按现金选最小值并保留等价解。不能只对商品应付求最小，再未经证明地贪心扣最多积分/代金券，称为完整现金最优。

记录候选总量、实际评估/安全剪枝覆盖、拒绝理由、最优账本、规则快照及完成标记。只有完整遍历或有可复核的完整安全剪枝证明后，才能给 `OPTIMAL_PROVEN`。时限内当前最好解只能是 `FEASIBLE_NOT_PROVEN`。

### 5.2 规模需要时接 OR-Tools CP-SAT

只有全部业务表达可无损编码为整数约束才启用；复杂舍入、区间、条件依赖用精确约束/允许元组/预计算表，不把近似模型说成真实规则。适配器需记录实际目标值、best bound、停止原因、模型/参数/规则版本并独立回放金额。

`FEASIBLE` 不证明最优；`UNKNOWN` 不证明无解；`MODEL_INVALID` 是建模错误。`OPTIMAL` 也不能单看字符串：官方合同允许达到设置的 gap 后返回此状态。禁止用未达整数精确最优的非零 gap 解放行；可增加“在同一资源快照/允许范围内是否存在更小整数现金支付”的反证求解，证明无更优解。不能比较经显示舍入后的金额假装零 gap。[CP-SAT 官方说明](https://developers.google.com/optimization/cp/cp_solver)、[状态与目标界](https://github.com/google/or-tools/blob/stable/ortools/sat/cp_model.proto)、[gap 参数](https://github.com/google/or-tools/blob/stable/ortools/sat/sat_parameters.proto)

求解器证明的是准确编码与已列候选域，不证明所有现实商家价格。每 SKU 范围最优与适配推荐集内的跨 SKU 最低分别记录；跨产品最低不表示同一配置比较，不等于所有型号/全网最低，也不能给不同产品套同一报价。某店某时点不等于长期最低；预算快照不等于已预占交易资源。哈希和日志是可追溯证据，不宣称已由独立形式证明器验证。

### 5.3 InternalQuote 与 CustomerQuoteSummary

InternalQuote 为每 SKU 分别保存原始条件、推荐集/适配依据引用、四级名称确认来源及实际规则/候选版本、资源快照/允许范围与目标版本、内部约束、分层账本、资源消耗/余量、选项与拒绝理由、求解及回放证据、有效期、来源权限与哈希。ComparisonManifest 另记录跨SKU比较与完成覆盖；不能用一份报价引用替代多个型号的独立结果。按 tenant/store/角色访问；运营者和客户视图不返回内部阈值或审批细节。

CustomerQuoteSummary只允许显式获准字段：quote_ref/quote_version、SKU/配置、quantity、客户可见门店渠道、currency、目标metric/version、`merchandise_total_minor`、`mandatory_fees_minor`、`order_total_before_payment_minor`、`credits_applied_minor`、`cash_due_now_minor`、其等值投影`customer_payable_minor`、资源快照/允许范围安全引用、获准资源消耗/余量与旧机价值说明、服务端格式化的`formatted_customer_payable`、客户须知的组成/资格/有效期、必要限制、限定现金最优范围及对客来源摘要。`formatted_customer_payable`继续是唯一现金口播格式化值，明确说“本次现金支付”，不让LLM算差额；其他组成金额由服务生成获准breakdown句。客户构成需单独白名单，不能把内部账本原样删几个字段后返回。脚本的`customer_quote_ref = quote_ref`只是同一报价的语义别名，必须绑定同一quote_version；各金额属于同一分层账本，不独立改写或另建payable_minor字段。客户摘要金额与资源使用方案必须同版本一致，未选并列路径不冒称已执行；详细字段见唯一逻辑合同。

CustomerQuoteSummary的存在与有效性不自动授权发送云模型、公开软文或海报。每个消费方检验purpose、destination/provider、region、字段白名单、有效期、撤销状态和当前版本；不同客户资格的报价不可复用给另一客户。只把`quote_status=VALID_OPTIMAL`、当前独立validation通过且本次用途的`client_quote_allowed=true`快照送入真实报价内容和客户脚本；其他结果只返回补充/复核动作，不生成带金额的可发布稿。顾客可见的等价方案差异若需展示，应由服务单独生成获准摘要，不返回内部替代方案表。

### 5.4 正式购买方案与安全组合比对

唯一方案字段为`CustomerQuoteSummary.customer_purchase_plan`，Schema为`CustomerPurchasePlan`，工作流从`quote_context.customer_quote_summary.customer_purchase_plan`消费，不另造顶层同义DTO。它与同一quote_ref/version、validation、资源快照及目标版本绑定，服务端生成安全行与格式化文字，LLM只组织当前平台/人群/场景的话术。正式`marketing/full_package`至少交代：

- 四级名称各自适用、不适用或因互斥排除的状态、客户可见原因与有据来源别名；按规则说明销售折扣/补贴和支付工具性质，不能强行四级都减一次。未知资格/缺规则不写成不适用。
- 同一SKU的合法组合比较：最优方案、其他有解释价值的已核验组合、商品结算/抵付/本次现金/资源消耗差异及适用前提。真实只有一个合法组合时如实说明，不编造对手方案；内部仍须完成候选完整性核验。
- 适配推荐SKU的可比范围、应比较/已核验数量、未完成及不可比项、受限最低结论；对客只展示获准安全比较行，不能因只公开几行就把未完成候选当高价排除。
- 当前选定/待选最优方案、本次现金、旧机价值/积分消耗/余量、资格、条件和有效期；并列现金但资源消耗不同要说明差异，不暗选不可逆使用。

合同字段包括`level_rows`、`comparison_rows`、`comparison_coverage`及服务生成的`optimal_scope_sentence/resource_usage_sentence/conditions_sentence/valid_until_display`。对客行不是完整内部枚举账本，内部规则、完整候选与证明仍保存在受控服务器。所有比较句的金额来自对应冻结结果，当前方案口播仍只用`formatted_customer_payable`，模型不得心算。比较或披露授权不足时不生成可发布购买方案；即使已有单SKU有效金额，也不能把只有最终价的稿件验收为完整成品。平台/场景适配应改变讲解重点、利益点、对比顺序与行动引导，不能改变规则、金额或适用资格。

### 6.2 独立 quote_status

报价节点使用独立`quote_status`，不复用原稿件状态、整个任务状态或底层求解器状态。唯一逻辑合同的小写`status`只表示通信/流程结果；HTTP200或status=ready不能据此当报价可用。客户端必须同时检查下表报价状态、独立validation、版本及本次用途/目的地的client_quote_allowed。不报价任务为`quote_required=false, quote_status=null, quote_ref=null`，不使用not_requested报价枚举，不因P4未就绪阻断产品介绍/营销。

| quote_status | 明确含义 | 内容/脚本动作 |
| --- | --- | --- |
| `BLOCKED_SOURCE_UNVERIFIED` | 四级名称已确认，但实际金额、适用/叠加/核算顺序等规则未核验，含当前P4空模板；reason如`FOUR_LEVELS_PENDING`、`EMPTY_TEMPLATE`表示规则待取证，不再表示名称未知。 | 提示来源核验；禁止真实报价和实数脚本。 |
| `MISSING_INPUT` | SKU、quantity、currency、渠道、region、as_of、rule_timezone、资格或必要费用信息不足。 | 只追问允许公开的缺失字段；不补猜。 |
| `SOURCE_MISSING` | 必要价格/规则原文不存在、不可读或候选范围不完整。 | 补来源/权限；不可把缺失当无可行组合。 |
| `SOURCE_EXPIRED` | 价格/规则过期、有效期未核实或撤销；reason 区分具体情况。 | 拒用旧价；重新核验。 |
| `RULE_CONFLICT` | 有效来源冲突且无获准覆盖关系，或四级语义不一致。 | 受控人工核实，不对客披露内部冲突细节。 |
| `ACCESS_DENIED` | 当前主体无来源、门店、报价或用途权限。 | 阻断；不fallback绕过，不泄露私密源信息。 |
| `INFEASIBLE_PROVEN` | 完整有效模型已证明没有符合全部条件的解。 | 说明限定范围无可行组合；不给伪报价。 |
| `FEASIBLE_NOT_PROVEN` | 有候选但严格最优或完整业务门禁尚未完成，或只有内部条件试算；含solver已证但尚待独立复算。 | reason=PENDING_INDEPENDENT_VALIDATION且有quote_ref时进入validate；不得先发客户金额稿。 |
| `VALID_OPTIMAL` | 规则有效、销售/资源候选范围完整、本次现金确定、硬规则与独立回放通过且现金最优已证。 | 仍需目的授权后才提供CustomerQuoteSummary/脚本输入；正式marketing/full_package另检查customer_purchase_plan完整与可发布。 |
| `SOLVER_ERROR` | 数值/模型/服务内部错误。 | 可恢复错误，不冒充无解或成功。 |
| `CANCELLED` / `TIMEOUT` | 取消或到时终止，未完成可用报价门禁。 | 不接纳迟到旧结果；重新运行产生新run。 |

报价早已生成但消费时失效，应改为不可用并要求重算；数据库保留历史值用于审计，不向顾客继续显示为当前有效报价。父工作流按节点状态进入补信息、待规则确认、失败或继续等明确分支；不要直接写入原文档的同名状态枚举，也不能将“稿件审核通过”反向视为报价通过。

调用点固定为：solve取得引用 → validate独立复算 → client-view按本次用途取CustomerQuoteSummary → 需要脚本时script-input安全绑定 → 生成/本地模板 → verify-content核验金额与条件 → artifacts/finalize重新验源与版本。solve在独立validate前只可返回FEASIBLE_NOT_PROVEN；有quote_ref且reason=PENDING_INDEPENDENT_VALIDATION就进入validate，不要求先VALID_OPTIMAL造成循环。validate必须确认solver严格最优、完成独立回放及其他门禁后才提升VALID_OPTIMAL；solver未证最优时仅复算一致不能提升。每一步均使用第6.1节完整canonical路径，不另造接口别名。当前FourLevelsSpec的pending-source-verification专指实际规则待核验，可投影为界面price4_pending_source；四级名称仍为user_confirmed。真实报价请求对应BLOCKED_SOURCE_UNVERIFIED，而不是wrapper ready即放行。逐SKU状态与验证独立；跨产品比较完整性不得塞入或替代quote_status。

## 7. 向顾客讲产品和报价的 3 分钟脚本

本节规定生成合同，不编写假价格、假功能或现阶段可直接演的销售台词。

### 7.1 输入门禁与输出

输入只允许：先确认的平台/用户/场景与有据推荐结果、当前选定SKU的核验通过可对客FactSet、对应同一SKU且VALID_OPTIMAL/当前validation/目的地获准的CustomerQuoteSummary、顾客已表达需求、允许演示的实物动作、语气和门店可对客信息。若讲不同推荐产品，每个产品分别绑定自己的事实、报价与比较范围；适配集最低只在完整覆盖时表述，不能当同配置或全网最低。P4内部底价、返利、预算、审批与其他门店资料不能进脚本；不允许云端的字段不能通过“改写”方式外发。脚本按customer_quote_ref绑定同一quote_ref/version，只消费服务端formatted_customer_payable，不让LLM重新格式化/算价。

输出 `CustomerDemoScript` 包含：总计 180 秒的分段、每段目的、可照读文本、实际产品演示动作、给顾客看的画面、产品事实引用、报价/资格/有效期版本、异常应对、需店员核对项。先生成不含自由数字的结构化槽位，由代码从冻结事实和报价填金额/数值，再核验所有数字及条件，避免LLM自行重算或改价。

建议节奏：

| 时间 | 必须完成的内容 |
| --- | --- |
| 0-20 秒 | 确认顾客任务与讲解范围。 |
| 20-45 秒 | 核对完整型号、相关配置及演示机与拟售SKU关系。 |
| 45-85 秒 | 讲一个有依据的相关利益点、必要条件并执行产品验证。 |
| 85-120 秒 | 依据真实观察选择成功/未完成分支，说明使用边界。 |
| 120-155 秒 | 核对资格与资源，分别解释商品结算、已核验抵付、本次现金及旧机/积分消耗、条件和限定最低范围；不确定就停止金额段。 |
| 155-180 秒 | 说明有效期、复述适用前提与下一步行动；条件变化需重算。 |

无有效报价时，只生成获准产品介绍与缺失条件提示，不编完整报价段，也不将缺失脚本说成已交付的完整3分钟报价演示。正式marketing/full_package还须消费当前获准customer_purchase_plan，解释四级适用和组合比对后的选择，不能只读一个最终价；若180秒内需压缩，使用服务获准的精简比较句并将完整安全方案随稿交付，不删必要资格/资源消耗说明。不得口播“准确率95%以上”作为该次报价可靠性的替代。

### 7.2 修改、有效期与新店员验收

改产品、资格、门店、渠道、时点、规则、目标metric/version、资源快照/允许使用范围或金额后旧脚本失效；重算、重填槽位、重核再导出。保存/取消/重开验证实际文稿、快照与版本一致。用户临时要求加无依据优惠或内部底价时不得照写。

开发完成后让未参与设计的新店员用实际产品与应用演练，确认不靠工程师口头补充能讲清产品、确认条件、解释实付和有效期、识别异常并取得正确摘要；记录实际时长与卡点后修订。未完成真实演练不声称“拿到即可照演”。三分钟是脚本时长，不能偷换成引擎已验证响应时间。

## 9. 大于95%的独立验收

### 9.1 统计单位与成功条件

验收建议以**端到端、可完整定价的用户任务**为单位：从确认平台/用户/场景、据证筛选适配推荐开始，推荐适配与范围、每SKU配置/资格/销售规则、同一核验资源/允许范围、金额舍入/商品结算/抵付/本次现金/资源消耗与余量/严格现金最优证明、跨SKU比较覆盖与结论、来源时效均正确才算1个成功。多SKU请求只把容易完成的SKU当成功样本、遗漏或静默排除难报价的适配候选，不能让整任务通过；每SKU正确率仅作分层诊断。不能只测算术或让同一LLM自评。

冻结验收集之前定义 `n_quoteable`（金标判定可完整报价且在承诺范围内）、`n_exact`（全链正确且达金标最优）、`n_issued`（实际给出完整报价）：

```text
端到端正确率 = n_exact / n_quoteable，必须严格大于0.95
覆盖率 = n_issued / n_quoteable
已出报价正确率 = n_exact / n_issued，仅作辅助
```

本可定价样本的拒答、超时、局部金额、未证最优均算失败，不从分母删除。缺失/冲突/过期/无权限/资格未知等安全挑战集单列正确阻断和错误放行；正确拒答不混入报价成功分子。

建议首轮冻结至少 **200个可完整定价样本**，成功至少 **191/200=95.5%** 才满足这个样本上的严格大于95%；190/200恰为95%，不通过。若样本量不是200，最少成功数是 `floor(0.95*n)+1`。这是实施建议，实际来源若不足以支持代表性独立样本，报告受阻和范围，不能复制同题凑200或捏造业务规则。安全挑战样本另计，不占这200个正向样本。

191/200不等于“以95%置信度保证真实正确率大于95%”。报告样本量、抽样、分层和置信区间；若需置信下限也超过95%，需预先另定置信水平与样本设计。小样本/少失败可用精确二项区间，不能只看显示百分数。[NIST比例置信区间](https://www.itl.nist.gov/div898/handbook/prc/section2/prc241.htm)

### 9.2 金标和硬门槛

金标由有权限业务核验者依据独立原文确认，并用与生产实现不同的精确参考枚举/算术oracle验证。不能把同一计算器的结果抄成金标。开发集与冻结验收集分开；预先固定重试策略，不反复跑后只留最好一次；争议样本先仲裁再计分。

**确定性算术、适用硬规则、越权/机密泄漏、无依据报价、错SKU/资格/币种、遗漏必计费用、重复扣回收值/积分、虚构当前资源或旧机最终值、跨SKU资源快照不同却同域比较、未证现金最优却宣传最低、过期冲突放行，固定验收集中均要求零错误。** 总体大于95%不能抵消已知关键错误。发布门槛不是对所有未来任务零风险的保证；规则或范围变化后重测。

现金语义专项夹具至少包括：商品结算最低与现金最低排序不同；销售减项积分与支付抵付不得重复记账；代金券与同一旧机价值只扣一次；未来奖励/回收初估/未到账券拒用；未知运费阻断及积分使用改变运费的合法组合整体求最优；固定资源池下跨SKU反事实比较与多件合购总量约束；并列最低现金的消耗/余量说明；customer_payable_minor与cash_due_now_minor严格相等及唯一口播字段；资源变化后旧脚本失效。独立oracle须冻结同一目标版本/顾客资源和允许范围，既验证账本恒等式，也验证完整合法域内不存在更低现金方案。

正式成品还要检查customer_purchase_plan的四级状态/依据、同SKU合法组合安全比较、跨适配SKU覆盖范围、选定方案/现金/资源/条件/有效期与平台/人群/场景话术一致；只给最终价、无价介绍冒充完整包、未知条件伪造替代组合或把不完整范围称为全域最低均不通过。真实只有一个合法组合的有据说明可通过组合说明要求，不代表可以跳过来源和候选完整性。内部完整枚举/证明不得为“可解释”而直接公开。

至少分层覆盖：四级名称已确认但规则未核验、核算语义和真实顺序、四项不能默认叠加、换新国补不得凭常识推定、平台/用户/场景先确认、有据适配与不适配低价排除、每SKU精确最优、部分SKU缺价时比较覆盖不足、跨产品不得冒充同配置/全网最低、相近SKU、门店/渠道/时点、资格、互斥依赖、cap/floor、舍入尾差、必计费用/税费、预算/利润、等价解、完整分页、缺失/冲突/过期、精确枚举/CP-SAT状态、修改失效、租户目的授权及脚本SKU/金额绑定。

所有真实模型或接口调用仅在凭证、数据用途和费用授权已具备时运行；mock合同通过不能冒充真实知识库端到端通过。当前四级名称已确认，但P4已读资料仍为空模板、实际价格与组合核算规则未核验，只可完成合成与阻断测试；真实报价开关保持关闭，不能把用户确认名字当规则通过，也不能把真实报价正确率、实数脚本和新店员演练标通过。
